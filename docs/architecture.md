# 実装方針

## 最上位の要件: 50KB と通信の最小化

全体サイズと通信量の制約を、追加機能や演出より優先します。
**配布物の合計を 50KB = 50,000 バイト以下**に収め、ゲームを端末内だけで進められる構成とします。
初回取得とキャッシュ完了後のオフライン再起動を、初回公開の必須条件にします。

サイズは HTTP 圧縮前の公開ファイルのバイト数を合計します。
HTML・CSS・JavaScript・Service Worker と、追加する画像・アイコン・manifest などをすべて含めます。
分割ファイルや遅延読み込みの追加機能も上限の対象であり、外部配信へ移して計測から外しません。
開発用ソース（生成物と別に管理する場合）、文書、テスト、Git 履歴、ブラウザーの保存データは含めません。
現在は `src/` 全体が配布物です。将来、最小化のための生成工程を導入した場合は公開する成果物全体を計測します。

HTTP ヘッダーや TLS の通信量はこのファイルサイズ上限に含めず、実際の転送量を公開環境で別途測定します。
初回取得時の重複ダウンロード、再訪時の再取得、更新確認・更新の通信量も確認対象です。
公開前の CI に容量チェックを追加し、上限超過時は公開を止めます。現在は方針のみで、CI チェックは未実装です。

## 基本構成

HTML・CSS・JavaScript（ES Modules）で作る、ブラウザー内で完結する静的サイトとします。
配信するファイルを `src/` に集め、GitHub Pages にはこのフォルダだけを公開します。
`docs/` は開発文書用であり、Pages の公開元には使用しません。

初期構成にはフレームワーク、パッケージ管理、ビルド処理を導入しません。
容量制約と更新管理のために必要になれば、公開物の最小化や内容ハッシュの付与に限定した小さな生成工程を追加できます。
その場合も元のソースには説明コメントを残し、可読性を保ちます。
実行時に外部のライブラリ・API・画像・Web フォントを取得せず、Wasm や大きなゲームエンジンは採用しません。
クライアントのルーティングも導入せず、1 ページで完結させます。

## 現在のソース

| ファイル | 責務 |
| --- | --- |
| `src/index.html` | 文書構造、初期案内、遊び方 |
| `src/main.js` | 操作を持たない盤面配置の描画 |
| `src/styles.css` | 初期画面の外観とレスポンシブ表示 |

現在の盤面は見本のため `aria-hidden` としています。
実際のゲーム実装では、カードを操作・読み上げできる HTML に置き換えます。

## ゲーム実装時の責務

次の境界を設けますが、未使用のファイルや汎用フレームワークを先に作りません。

| 配置予定 | 責務 |
| --- | --- |
| `src/game/` | カード、配札、合法手判定、状態遷移、勝利判定。DOM や保存処理に依存しない |
| `src/ui/` | 盤面描画、選択、クリック・タップ・キーボード操作、案内 |
| `src/storage.js` | JSON の読み書き、保存形式のバージョン確認と復元検証 |
| `src/sw.js` | 公開ファイルのキャッシュ、オフライン起動、版の切り替え。ゲームの保存とは分離する |
| `src/main.js` | 初期化と、UI・ゲーム状態・保存をつなぐ処理 |
| `tests/` | ルールと状態遷移の自動テスト |

ゲーム状態を唯一の正として保持し、DOM の並びからルールを判断しません。
ルール関数は現在状態と操作を受け取り、成功時は新しい状態を返す純粋関数を基本とします。
不正な移動では状態・履歴・手数を変更せず、失敗理由を UI で案内します。

カードは表示文字列から判定せず、スートの固定識別子と数値ランク（1〜13）を使います。
各カードには一意な ID を持たせ、ゲーム中は常に 52 枚が重複・欠落なく存在することを守ります。
状態は通常の配列とオブジェクトで表現し、継承やイベント基盤の導入は避けます。

Undo／Redo は成功した手ごとの盤面スナップショットで始めます。
52 枚の小さな状態なので、複雑な逆操作よりも再現性と読みやすさを優先します。
履歴の対象、手数、経過時間の扱いは [ゲーム仕様](game-spec.md) を正とします。
タイマーなど短周期の表示は個別に更新し、盤面再描画でキーボードフォーカスを失わせないようにします。

## コメントと日本語

- シンプルな構造、美しい設計、可読性の順に優先します。
- ファイルと、1 行程度の自明な関数を除く関数には説明コメントを付けます。
- コメントには目的・前提・判断理由を書きます。特に複数枚移動の上限や履歴の扱いを説明します。
- すべてのテキストは UTF-8、改行は LF とし、HTML に `lang="ja"` と `charset="utf-8"` を指定します。
- 日本語文言とスート記号は Unicode の文字列として扱い、バイト単位の分割や切り詰めを行いません。
- 通常の文言挿入には `textContent` を使い、保存データを HTML として解釈しません。
- フォントは端末の日本語対応フォントを使用します。絵柄は HTML・CSS とスート記号で表現し、画像なしで始めます。

## 公開パスと保存

GitHub リポジトリは `teizu/free-freecell` とし、プロジェクトサイトの `/free-freecell/` を配信時のサブパスとします。
CSS、JavaScript、将来の画像、ページ内リンクは `./` などの相対パスにします。
ルートを指す `/styles.css` のような参照は使いません。

ゲーム状態の保存は `localStorage` に限定し、アカウントやサーバー API は用意しません。
同一 GitHub Pages ホストには複数のサイトが置かれる可能性があるため、
保存キーにアプリ名・配置パス・保存バージョンを含めます（例: `freecell:/free-freecell/:v1`）。
保存できないブラウザー設定でも、案内を表示して現在のゲームを続けられるようにします。
復元時は JSON の構造、スート、ランク、枚数・重複、ホームセルの順序、履歴の整合性を検証します。
不正な内容を一部だけ読み込まず、復元を見送って新しいゲームを開始し、理由を通知します。
複数タブの同期、統計、クラウド保存は初回の対象外です。

## オフラインと更新

配札・カード操作・履歴・ゲーム保存・時間表示はネットワークに依存させません。
新しいゲームもページの再読み込みを行わず、端末内で配札し直します。

初回のオンライン取得時に、Service Worker でゲームに必要なすべての公開ファイルをキャッシュします。
キャッシュ準備の完了を確認してからオフライン利用可能と案内します。
以後は保存済みのアプリを優先して使用し、ブラウザーを閉じた後でも、ネットワークなしで再起動・新規ゲーム・保存したゲームの続行を可能にします。
Service Worker とキャッシュの対象はこのアプリの配置パス内に限定し、同一オリジンにある別アプリのデータを削除しません。

通信は初回取得と更新確認・必要な更新ファイルの取得に限定します。
アプリ独自の定期ポーリングや操作ごとの更新確認は行いません。
起動に伴うブラウザー標準の Service Worker 更新確認を基本とし、確認に失敗してもゲームを開始・継続できます。
JS・CSS は内容が変わった場合だけ URL を変更し、同じ内容をキャッシュから再利用できるようにします。
初回表示とキャッシュ準備で同じファイルを二重に取得していないかも実測します。

新版のファイルがすべて揃ってから切り替え、異なる版の HTML と JS を混在させません。
旧版で開いているページがなくなってから新版を有効にする標準の待機動作を基本とし、対局中の強制更新は行いません。
旧版のキャッシュは利用中のページがなくなってから、このアプリのものだけを整理します。
キャッシュの更新を理由にゲームの保存データを消さず、保存形式の互換性は別に検証します。

ローカルコピーは `localhost` の HTTP サーバーから起動します。必要なファイルとサーバーが手元にあれば、インターネット接続は不要です。
ES Modules と Service Worker を使うため、`file://` での HTML 直接起動は対象外です。
PWA のインストール画面や専用アイコンはオフライン動作の前提とせず、後から検討します。

未取得の端末やキャッシュが消去・退避された端末では、公開サイトのオフライン起動はできません。
ブラウザーが Service Worker や保存を禁止している場合もオフライン再起動を保証せず、その状態を案内します。
この場合でも、読み込み済みの画面でのプレイやローカル HTTP での利用は継続できる設計にします。

## 検証

初期画面では JavaScript の構文、UTF-8、相対参照、HTTP 配信、文書間の整合性を確認します。
機能実装時は容量チェックと、キャッシュ完了後のオフライン再起動、ゲーム操作中の通信がないことを必須の検証にします。
ゲーム実装時には Node.js 標準の `node:test` を使い、ルールの境界条件を自動検証します。
Node.js 24 を開発時の基準とし、ゲームの配信自体には Node.js を必要としません。
テスト導入時に `package.json` の `type: module` と実行スクリプトを追加します。

初回公開前にはデスクトップとスマートフォンで操作・描画を確認します。
クリックとタップ、キーボード、保存失敗、破損データ、Undo／Redo 後の勝利状態を個別に検証します。
ブラウザーで未確認の条件を、構文チェックだけで動作確認済みとは扱いません。
具体的な確認条件は [実装計画](roadmap.md) に記載します。
