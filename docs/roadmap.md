# 実装計画と受け入れ条件

最初に規則と状態管理を固め、その後に操作と保存を加える。ゲーム規則の変更と見た目の変更を分離し、各段階で動作を確認できる小さな単位で進める。

## 全段階に共通する最上位の条件

- 配布する全静的ファイルを、圧縮前の合計 **50KB（50,000 バイト）以下**に保つ。集計対象は [ゲーム仕様](game-spec.md) に従う。
- 外部ランタイム、画像、Web フォント、API に依存せず、ゲーム操作と保存を端末内で完結させる。
- 初回取得とキャッシュ保存後のオフライン再起動、およびローカル HTTP サーバーでのインターネット不要のプレイを、初回公開の必須条件とする。

ゲーム機能の実装と並行して配布サイズの自動集計を追加し、CI で 50,000 バイト超過時に失敗させる。上限ちょうどと 1 バイト超過の境界を検証し、集計対象に Service Worker や任意の追加アセットも含める。現在、この自動チェックとオフライン機能は未実装である。

## 現在の到達点

初回コミットで用意したものは、ローカル Git リポジトリ、`src/` の初期画面、仕様・設計・公開手順の文書である。カードの配布、移動、履歴、勝利判定、保存、オフライン再起動は未実装であり、この段階をプレイ可能な完成版とは扱わない。

## 段階 1: ゲームの規則

DOM に依存しない処理でデッキ、初期配列、ゲーム状態、合法手判定、移動、勝利判定を実装する。シャッフルには Fisher–Yates 法を用い、テスト時に乱数を差し替えられる形にする。ゲーム番号の互換機能は追加しない。

受け入れ条件:

- 52 枚が重複も欠落もなく配られ、各列の枚数が `7, 7, 7, 7, 6, 6, 6, 6` になる。
- 赤黒交互・1 段下の場札への移動、空列への任意ランクの移動、空きフリーセルへの移動が成立する。
- 同色、同ランク、2 段以上の差、埋まったフリーセル、同じ移動元と移動先を拒否する。
- ホームセルは同一スートの A から 1 段ずつ進み、異なるスート、ランク飛ばし、ホームセルからの通常移動を拒否する。
- 連続部分が途中で崩れている場合はまとめて移せない。移動可能枚数のちょうど上限は許可し、上限より 1 枚多ければ拒否する。
- 空の移動先を空列数に数えないこと、移動後に空になる元列を数えないことを検証する。
- 不正な操作で入力状態を変更しない。合法手の後も盤面全体で 52 枚を保つ。
- ホームセルの合計が 51 枚では未完了、正しい 52 枚で勝利になる。

## 段階 2: 一局を操作できる画面

状態から盤面を描画し、クリック・タップ・キーボードで移動元と移動先を選べるようにする。新しいゲーム、最初から、手数、時間、勝利表示を実装する。

受け入れ条件:

- マウスとタッチで、場札・フリーセル・ホームセルへの合法な移動を行える。
- Tab、Enter、Space、Escape で選択、移動、選択解除を行える。移動後もフォーカスを見失わない。
- 不正な移動の理由を通知し、盤面・手数・選択状態は仕様どおりに維持する。
- 「最初から」は元の配りを再現する。進行中の置き換えをキャンセルすると元のゲームが残る。
- 時間が最初の成功した手で始まり、非表示時と勝利時に止まる。手数は成功した移動だけ増える。
- 320 px、768 px、1280 px 幅で必要な操作に到達できる。狭い画面では盤面だけの横スクロールを許容する。
- 長い列、200% ズーム、日本語の表示、スートの読み上げ、フォーカス表示を確認する。

## 段階 3: 履歴と保存

戻す・やり直す操作と、ブラウザー内の保存・復元を追加する。履歴には盤面のスナップショットを使う方針とし、専用の差分形式や複雑なコマンド階層を先に導入しない。

受け入れ条件:

- 1 枚の移動も複数枚の移動も、1 回の「戻す」で移動前に戻る。
- 「戻す」「やり直す」で手数が履歴位置と一致し、別の移動後はやり直し履歴がなくなる。
- 勝利を取り消すとプレイ可能になり、時間も再開する。やり直しで勝利に戻れる。
- 再読み込み後に盤面、初期配列、履歴、手数、時間が戻る。閉じていた時間は加算しない。
- 保存禁止・容量超過でもゲーム操作が継続し、保存失敗の通知を出せる。
- 壊れた JSON、未知の形式、重複カード、欠落カード、不正な履歴を安全に扱える。
- ゲーム専用の保存キー以外を変更しない。

## 段階 4: オフライン起動と通信量

Service Worker を追加し、起動に必要なファイルをキャッシュから利用できるようにする。新版への切り替えを含めて実装し、現在のゲームを壊さず更新できることを確認する。

受け入れ条件:

- キャッシュのない状態で初回取得を完了させ、オフライン利用の準備が完了したことを確認できる。
- その後にブラウザーを閉じ、ネット接続を切ったまま同じ URL を開いて起動できる。ページを開いたまま接続を切る確認だけでは合格にしない。
- オフラインで新規ゲーム、保存したゲームの再開、移動、最初から、戻す、やり直す、勝利まで操作できる。
- ローカルにコピーした配布物を localhost の HTTP サーバーで起動し、インターネット接続なしで一局を遊べる。
- ブラウザーの Network 記録で、ゲーム操作に起因する通信、外部リソース取得、定期的なポーリングがないことを確認する。
- 初回、変更のない再訪、新版への更新について、要求数と実転送量を別々に記録する。圧縮前の配布サイズと混同しない。
- 更新確認に失敗しても旧版で遊べる。新版がある場合も対局中に強制更新せず、切り替え後に旧版と新版が混在しない。
- 初回未取得、キャッシュ保存失敗・削除時の限界を案内し、既に読み込み済みのゲームを継続できる。
- キャッシュの操作対象をこのアプリの範囲に限定し、同一ホストの別サイトのキャッシュを削除しない。

## 段階 5: GitHub Pages での公開確認

公開手順は [deployment.md](deployment.md) に従う。GitHub リポジトリ `teizu/free-freecell` の作成と初回 push は完了している。実際の Pages 公開状況は未確認であり、ゲームの公開確認はこの段階で行う。

受け入れ条件:

- GitHub Pages のプロジェクト URL `https://teizu.github.io/free-freecell/` で CSS と JavaScript が読み込める。
- 公開 URL を直接開く場合と再読み込みする場合の両方で起動する。
- 公開したページで配り、移動、戻す、やり直す、再開、勝利までを確認する。
- 公開対象の全ファイルが圧縮前で合計 50,000 バイト以下であり、CI の容量チェックも通っている。
- 公開 URL でも、初回キャッシュ保存後のオフライン再起動と、更新時の通信・切り替えを確認する。
- Chrome・Edge・Firefox・Safari の実機または実ブラウザーで主要操作を確認し、未検証の環境は記録する。
- Android Chrome と iOS Safari でタッチ操作と縦横の表示を確認する。
- ローカル確認だけで本番公開済みと判断せず、デプロイの成功と実際の公開 URL を確認する。

## 追加機能の検討順

最初の公開後、操作上の問題を先に改善する。その後、50KB と最小限の通信量という上位要件を満たす範囲で、ドラッグ操作や操作補助を検討する。自動移動を加える場合は、後の手を妨げない条件と履歴上の扱いを先に定める。ヒントやソルバーは、単純な合法手の案内とクリア可能性の保証を区別して設計する。ホーム画面へのインストール UI やマニフェストは任意の追加機能とし、必須のオフライン起動とは区別する。

## 検証の方針

規則・履歴・保存データ検証には、入出力と境界条件を確認する自動テストを用意する。Node.js 標準のテスト機能を第一候補とし、必要性のないテスト用依存は増やさない。DOM を持たないテストが通っても、表示やタッチ操作の確認を代替したとは扱わない。

見た目だけの小さな変更に、実装をなぞる自動テストは追加しない。操作仕様を変えた箇所は対応する条件を検証し、確認環境と未検証範囲をコミットや作業報告に残す。
